# Property journal correctness candidate

Base: `801f7c47`; branch `codex/pr494-property-journal-v3`. Prerequisite: incoming-occurrence removal commit `2a27b7a8` (locally `c2975a19`), which removes the last child/property occurrence without executing key equality. Independent graph-oracle test commit `40043663` is included as `34642160`. No original tests were modified. This commit is the correctness stage; journal hot-path specialization is separate.

The baseline is a desired occurrence sequence before recursive attachment finishes. Nested reconciliation now starts from a property-scoped journal of occurrences actually installed, so retaining an unpublished child adds its missing edge and replacing a partially published collection drains only existing edges. Incoming additions/removals update the journal immediately after the ownership mutation, before descent. Owner identity and baseline revision stop superseded continuations. Seeding creates empty installed journals alongside its desired baselines; release snapshots those installed occurrences. Nested completion refreshes the journal's order and indices for a possible further nested write.

The journal uses pooled records and reusable array-backed entry storage. Each child has a last-entry pointer, while a doubly linked sequence preserves occurrence order. Add/remove are expected O(1), with reference equality and no user key equality. Initialization/copy/completion are O(affected-property occurrences). There is no whole-graph scan, retry loop, or linear active-depth membership lookup. Dictionary operations assume ordinary expected hash-table costs. The existing reachability algorithm and its baseline scans are unchanged. Initial pool/capacity growth allocates; warmed capacities are retained per thread. An interrupted operation retains at most one partial journal per affected property/ownership epoch until a successful reconciliation or owner release clears it. The candidate does not yet specialize single occurrences or defer materialization to actual reentry.

## Inline storage follow-up

The next commit stores zero/single occurrences directly in the pooled journal record and only materializes the linked entry list and per-subject dictionary on a second installed occurrence. OwnershipGraph stores the first journal directly and creates a dictionary only when another property is active concurrently. Normal single-property operations avoid journal-map hashing and single-occurrence operations avoid subject hashing. Membership remains expected O(1) at arbitrary nesting depth. Multi-occurrence capacities remain reusable after reset. Empty seed journals no longer rent an unnecessary temporary occurrence list. No speculative lazy reconstruction is used.

Verification after these changes: full Tracking **808 passed / 20 failed / 828**, with the same original failure names; the 21 focused blocker/oracle/journal cases pass. Production delta over correctness: +90/-40, net +50. This is a structural allocation/hot-path reduction; no benchmark was run, so CPU or allocation gains are not quantified.

## Failed-seed recovery follow-up

Four new probes confirmed that a retained child whose authoritative getter failed before its baseline was captured stayed partially seeded on parent retry, for both the same collection object and a new collection and at one or two levels of attachment. This follow-up addresses that earlier scope limit.

A lazy failure-only map records the subject's ownership epoch when seeding throws. Reconciliation resumes a failed retained subject by first settling its captured property journals and then seeding missing baselines. Removing the failure marker while recovery runs terminates cyclic back edges; failure restores the marker only for the same current owner. Release removes it. Both retained occurrences and an additional edge to an already partially seeded subject can trigger recovery. Normal retained children perform an empty-map check and do not reread structural properties or repeat ownership/revision lookups for nonexistent recovery.

The original attach's remaining ordered handlers, subject event and property notifications are queued even if descent throws. They remain in that original operation's history; retry resumes only graph seeding and replays no notification. The getter exception retains its identity and precedes later callback/observer failures. Claim cleanup excludes subjects with a queued release so property/lifecycle delivery retains its context; the existing combined seeding/lifecycle/property failure-order regression caught and verified this requirement.

Six focused tests pass: same/new parent collection retry, direct/nested failures with a back-edge cycle, already completed sibling attachment exactly once, Registry descendant restoration, repeated failure while acquiring independent support followed by original-edge removal, and exact before/after/event/property callback history once on the original failure. Full Tracking after final code changes: **814 passed / 20 failed / 834 total**, exact same 20 failure names as the previous frozen stage. TRX: `property-journal-v3-recovery-final.trx`; log: `/private/tmp/property-journal-v3-recovery-final.log`.

This is not a strong exception guarantee for arbitrary getter failures: a failed graph operation can leave an owned component partly seeded, with original notifications delivered; a later parent retry resumes it, or detach releases its installed edges. Recovery work is proportional to the affected failed subjects' structural properties and captured/desired occurrences, using the existing property reconciler; there is no automatic retry loop or whole-context sweep. The failure map allocates only after a failure and retains capacity after successful recovery. Production delta over inline storage: +87/-12, net +75, in four files. No benchmarks were run.
